# 汇总行改成「不重不漏的分区」(顺带: --no-preflight 不再冒充计划)

**日期**: 2026-10-05
**触发**: 用户盯着 dry-run 的输出问:「`组织邀请: 计划邀请 2 人` 这里的计划邀请是什么
意思、数据从哪来、ARCHITECTURE 里提了吗? 我觉得这个定义很模糊。」

## 现象

`--no-preflight` 跑一个 4 行的表:

```
组织邀请: 计划邀请 4 人 | 已是成员 0 人 | 已有待处理邀请 0 人 | 失败 0 人 | 跳过 4 人
```

**「计划邀请 4 人」和「跳过 4 人」是同一批人。** 字面像 8 个人, 实际表里只有 4 行。
换个大一点的表更明显: 12 行的表, 各桶相加读出来是 **22 人**。

而且 `--no-preflight`(没预检)也算「计划邀请」—— 那个模式下脚本根本没查过谁在组织里,
"计划"两个字纯属给它贴金。

## 原因

1. `S_PLANNED` 同时被放进了 `ORG_SKIP`, 而汇总末尾那一段就是
   `sum(counts.get(key, 0) for key in ORG_SKIP)`: 于是 planned 既单独列了一遍、
   又被末尾总数算了一遍。`already_invited` 同样被数了两次(它也在 `ORG_SKIP` 里)。
2. `planned` 一个状态被两种模式共用: 预检过的 dry-run 和 `--no-preflight`。
3. ARCHITECTURE 里**从来没写过**汇总行由哪些状态加起来 —— 只有 §五 那张「判定顺序」
   表和 `ORG_LABEL` 能反推, 而 `ORG_OK` / `ORG_SKIP` 的用途一个字没提。
   所以用户觉得模糊不是错觉, 是文档和实现两头都欠着。

## 处理

- **拆归类集合**(`inviter/outcomes.py`): `ORG_OK` / `ORG_SKIP` / `ORG_PENDING` /
  `ORG_UNTOUCHED` / `ORG_SETTLED`。`planned` / `unknown` 不再属于 `ORG_SKIP`。
- **新增状态 `S_UNKNOWN`**: `--no-preflight` 用它, 标签是「状态未知(未预检)」;
  `planned` 只留给预检过的 dry-run。
- **汇总行改成真正的分区**: 末尾不再放任何「桶」, 只放「**合计**」= 逐行结果的总人数;
  具名桶相加与合计之间的差额, 恰好是 `ORG_UNTOUCHED`(没联系方式 / 表里重复 /
  `--limit` 没轮到), 那三类在明细行里逐条列着。具名桶的措辞统一取自 `ORG_LABEL`
  (原先汇总写「已是成员」、明细写「已是组织成员」)。
- **断言钉住**: `run_output_tests.py` 把三种模式的汇总各数一遍, 断言合计 == 总人数、
  且差额恰好等于 `ORG_UNTOUCHED` 的人数; `run_module_tests.py` 断言五个集合 + `failed`
  覆盖全部状态且两两不重叠。

改完那 4 行的表是:

```
组织邀请: 状态未知(未预检) 4 人 | 已是组织成员 0 人 | 已有待处理邀请 0 人 | 邀请失败 0 人 | 合计 4 人
```

## 认知纠正

### 1. 我先把一个「故意的设计」当成了 bug

`--no-preflight --execute` 一起给时 `--execute` 会被忽略, 一封都不发。我一开始把它归到
「坑」里 —— 直到在 ARCHITECTURE §六 翻到作者自己写的原话:

> `--no-preflight` 时状态是「不知道」… 即使配了 `--execute` 也不会发请求(没预检就发等于盲发)。

**这是有意的, 而且已经写下来了。** 所以我不再建议「报错拒绝这个组合」(那等于推翻一个
写明的决定), 改成**保留行为、把话说出来**。

教训: 说「这里是个坑」之前, 先把文档搜一遍 —— 也许作者早就想过并且写了理由。
我要回答的还是「为什么文档里找不到」, 而不是「实现错了」。

### 2. 「写了警告」不等于「警告会出现」

代码里确实躺着一句 `注意: 本次带了 --no-preflight, 没有真的发出邀请(状态不明), 别拿这份当结果。`
—— 但它在 `mode == "execute"` 的分支里, 而那个分支必然 `needs_api == True`, 所以
`not needs_api` 永远是假: **死代码, 从来没打印过**。更糟的是同一条路径还会劝用户
「加 `--execute` 真正发送」, 而他刚加过。

判定这类问题的唯一办法是**真的跑一遍看输出**, 不能只看"这里有句警告"。

### 3. 一个词有两个含义, 它的数字就没法当账对

「跳过」曾经同时装着两种东西: 真没动的(重复 / 缺联系方式 / `--limit` 截断)和**计划要发的**。
于是那一行既不能相加、也不能解释 —— 用户问的正是这个。

现在立的规矩是: **汇总行必须是一个分区, 末尾的「合计」== 逐行结果的总人数**。
这条规矩写成了断言, 所以以后加状态时忘了归类会当场红, 而不是悄悄开始漏人。

### 4. 我自己新造的标签, 一眼就被用户看穿了

第一版把末尾那个桶改名叫「**本次没动**」, 结果用户贴回输出问「为什么是本次没动 0 人, 好
奇怪的表示」。他说得对, 两个毛病:

- 「本次没动」听起来在描述**整次运行**, 而 dry-run 本来就什么都没发 —— 于是一句话自相
  矛盾(整场都没动, 怎么还是 0)。它其实只描述**一类行**。
- 一个恒为 0 的桶就是噪音。旁边「已是组织成员 0 人」「邀请失败 0 人」读着正常, 是因为它们
  是关于**人**的否定判断(「没有这种人」); 而那一桶是关于表格和本次范围的。

结论: **汇总行末尾不要放「桶」, 放不会重复计数、也不需要解释的「合计」**。想要透明,
就把差额交给下面**带精确标签**的明细行去解释。

教训: 自己发明的、用户没见过的词, 风险比设想的大 —— 我为了修「含义模糊」引入了第二个
含义模糊的词。改用户可见文案时, 要么用他已经在明细行里见过的标签, 要么用「合计」这种
不需要定义的字眼。

### 5. 改文案会碰掉既有断言 —— 但别把断言的意图一起丢

汇总行从「失败 0 人」变成「邀请失败 0 人」之后, 既有那条
`必须不出现「邀请失败」` 断言红了 —— 因为汇总行现在**永远**有「邀请失败 0 人」这一节。
它原本的意图是「没有任何一行被报成失败」, 所以我没有删掉断言, 而是把判据换成真正的失败
痕迹: 汇总的明细行(`- 邀请失败: N 人`)和失败明细区块(`== 失败明细(按原因归类) ==`),
两者都只在真有失败时才打印。**意图保住, 判据更准。**

## 验证方式

拿 `git show HEAD:github_inviter.py`(拆分前的旧单文件)导出到临时目录, 和现在的版本跑
同一组 6 个用例(help / csv / xlsx / 列顺序 / 只有姓名邮箱 / `--no-header --cols`),
逐行 diff: 差异只有预期的三类 —— 逐行表的标签、汇总第一桶、汇总末尾桶;
`--help` 逐字节相同。**这是「只改了想改的」的硬证据**, 比读代码可靠。

## 回滚方式

改动全在工作区/一次提交里: `git checkout -- .`(或 revert 对应提交)即可。
输出会退回「计划邀请 4 人 … 跳过 4 人」那个读法。
