# 「待对方接受组织邀请」查不到头 —— 其实两处用户名拼写错了

**2026-10-04 下午(接同日的合并重构)** · 组织 `NEUP-Net-Depart` · 6 人名单全部落定

前置背景见 [`2026-10-04-merge-org-team-inviter.md`](2026-10-04-merge-org-team-inviter.md)。

> **脱敏说明**: 本日志里的姓名用 甲/乙, 用户名用 `u5er_na3e` / `user_name` 这类占位符。
> 但**保留了「哪几个字符被打反」的信息** —— 那正是这次要记的教训。

## 1. 现象

用户跑完 `--execute` 后反馈:

> 我第一次发回复这个
> ```
> == Team 加入: NEUP 2026(角色 member) ==
>   · 甲: 待对方接受组织邀请
>   · 乙: 待对方接受组织邀请
> ```
> 之后甲同学已进组织, 但是第二次发这个命令的时候, 输出还是这两行「待对方接受组织邀请」。

两次跑输出完全一样 —— 说明不是随机因素, 而是每次都走进同一个分支。

## 2. 我第一次猜错了方向(记下来当反面教材)

我第一反应是「GitHub 的成员**列表**有延迟, 快照里没他, 所以永远判待接受」,
于是给 `process_team` 加了一次**活查**: 拿不准时调
`GET /orgs/{org}/members/{username}` 单查这个人到底是不是成员。

**用户质疑:「你修改了脚本的什么, 我感觉是不是不用修改, 这是用户输入错误?」—— 他是对的。**

复盘这个错误:

| 我的假设 | 实际情况 |
|---|---|
| 成员列表会滞后, 导致误判 | **没有任何实测证据**。反证: 13:53 和 13:55 连跑两遍, 同一个人的「已是成员」判定两次都稳定 |
| 这次问题是这个滞后造成的 | **完全不是**。那两个人都在「用户名不存在」分支就 `continue` 了, 活查一次都没执行到 |
| 加活查是稳妥的防御 | 它给每个「有历史但不在快照里」的人多加一次 API 调用的失败路径 |

**已按用户判断整块还原**: 删掉 `is_org_member()`、`membership_cache` 参数、
`history` 参数(它只服务于「上次发过就活查」这个分支)、以及围绕它的三段式措辞
`invited_now`。现在 `process_team` 只信预检那一份成员快照, 回到最小改动。

> **教训**: 不要为自己没验证过的假设加防御性复杂度。先把因果查清(这次是数据拼写错误),
> 再决定代码要不要动。

## 3. 真正的原因: 两个用户名都拼错了

查下去发现**表里的用户名在 GitHub 上根本不存在**, 所以「等对方接受」是一句永远等不到的建议。

| 表里填的(占位) | `GET /users/{login}` | 真实用户名(占位) | 真实账号在组织里? |
|---|---|---|---|
| `u5er_na3e`(把 h/j 打反) | 404 | **`user_name`** | 是(已是成员, 只是没进 team) |
| `usr_naem`(把 a/c 打反) | 404 | **`usr_name`** | 是(已是成员, 只是没进 team) |

两个都是**相邻字符打反**。也就是说: 那两个账号本来就在组织里, 只是表里写错了名字,
所以脚本既认不出他们、也永远等不到「接受」。

改成正确拼写后重跑: **6 人全部已是组织成员 + 全部进入 NEUP 2026, 退出码 0**。

## 4. 认知纠正: 「网页搜得到」不等于「这个用户名存在」

用户拿 GitHub 网页搜索结果质疑:「不对啊, 那个打错的名字不就是用户名吗」。
把字段摊开后真相很清楚(下面用占位符表示同一个例子):

```
搜索 u5er_na3e            -> total_count=1
   登录名 login = 'user_name'            <- 真实账号
   主页 html_url = https://github.com/user_name
搜索 u5er_na3e in:login   -> total_count=0     <- 按登录名精确搜: 零结果
GET /users/u5er_na3e      -> 404
GET /users/user_name      -> 200

搜索 usr_naem             -> total_count=0
搜索 usr_name             -> total_count=1, login='usr_name'
```

GitHub 网页搜索是**模糊/全文**匹配, 并且会把**用户输入的那个词加粗高亮** ——
看上去就像账号名, 实际是「你搜的词」; 那 1 条结果是它把相近的账号推给你。

> **结论**: 判断用户名是否存在, **只认 `GET /users/{login}` 的 200/404**,
> 不要看网页搜索的条数, 也不要看高亮。

## 5. 留下的代码改动(只保留这一处)

新增状态 `用户名不存在`:

- 当某人不在成员快照里、且 `GET /users/{login}` 返回 404 时, 不再输出
  「待对方接受组织邀请」这种没用的话, 而是直说 **GitHub 上查不到这个用户名**,
  并提示「多半是拼错了; 也可能是对方把资料设为私密」(404 不排除后一种)。
- 该状态**计入失败**(退出码 1), 不会被悄悄咽掉。
- 控制台那一档分三种人话: `邀请刚发出, 等对方接受后重跑` /
  `还没成为组织成员(邀请待接受)` / `用户名不存在, 什么也做不了`。
- 新增 5 项回归测试(路径测试 17→22 项), 其中一项专门断言
  「不是成员就零 PUT、零多余 HTTP 请求」, 防止那次活查被无意加回来。

## 7. 顺带: 建了 git 仓库, 并修掉两个泄露风险

原来这个目录**不是 git 仓库**, 已 `git init` 并做了首次提交。提交前逐项核对忽略规则,
发现并修掉一个真实泄露风险:

> `.gitignore` 里写的是 `*.xlsx`, 而备份文件叫 `收集表.xlsx.bak` —— **不匹配**,
> 于是含真实姓名和邮箱的备份被 `git add -A` 暂存了。

已在 `.gitignore` 补上 `*.bak` / `*.tmp` / `*.orig` / `*~`, 并 `git rm --cached` 移除。

### 7.1 但第一次扫描漏了日志本身

更值得记的是: 我以为扫过了就安全, 结果**第一次扫描漏了** —— 那次的模式串只覆盖了
邮箱域名片段, 没覆盖**真实姓名和用户名**, 于是它们进了提交。

补救分三步:

**① 写扫描脚本** `_test/scan_pii.py`: 扫**所有被跟踪文件**。它抓出 3 个文件需要清理
(两篇日志 + 技能手册), 全部脱敏为占位符(甲/乙、`u5er_na3e`、`usr_naem`),
但**保留「哪几个字符被打反」的信息**, 教训仍然可读。

> **教训**: 「我扫过了」不等于安全。扫描的**模式串本身**也要被检查 ——
> 只扫邮箱就会漏掉姓名和用户名。

**② 扫描脚本自己又把 PII 存了一份**: 第一版 `scan_pii.py` 把那些真实姓名和用户名
**硬编码成模式串** —— 脱敏反而制造了新的泄露点。改成从**不入库**的词表读:

```bash
# .pii-terms 每行一个词, 已被 .gitignore 挡住, 绝不提交
python _test/scan_pii.py     # 退出码 0 = 干净; 1 = 有文件命中; 2 = 没有词表
```

**③ 重写 git 历史**: 脱敏只改了最新提交, **旧提交里仍然留着真实信息**
(用 `git grep <词> $(git rev-list --all)` 查出来的)。仓库没有远端, 所以安全地重写了:
把干净版文档替换进两个提交, 删掉临时分支, `git reflog expire --expire=now --all` +
`git gc --prune=now`, 让旧对象彻底消失。

验证: 对**所有可达提交**逐个 `git grep` 那些姓名/用户名, 结果全部干净;
旧提交对象 `git cat-file -t` 已查不到。

> 注意: 重写发生在**任何远端克隆之前**(这个仓库从来没有远端)。如果以后有人拿到
> 重写之前的副本, 那份副本里仍然有这些信息 —— 这点无法补救, 只能靠不分享旧副本。
