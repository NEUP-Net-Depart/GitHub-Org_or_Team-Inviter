## 3. 离线测试台抓到的 5 个真 bug

写了 40 项命令行测试 + 11 项落盘测试(`_test/` 下, 交付前删除)。抓到的都是真问题:

### 3.1 `build_records` 把两个位置绑错了名字(最要命)

```python
# 错: classify_cell 返回 (邮箱, 用户名), 这里把「用户名」那格绑到了 login 上
login_of_login_col, _ = classify_cell(login_raw)          # 实际拿到的是 email 槽
login_of_email_col, _ = classify_cell(email_raw)          # 实际拿到的是 login 槽
```

后果: **每一个用户名都被丢掉**, 所有行退化成「只有邮箱」。
表面症状极具误导性 —— 打印出来是「用户名列内容看不懂, 已忽略: zhangsan」,
看起来像正则或表格的问题, 其实是解包解错了。修正为:

```python
email_from_login_col, login_from_login_col = classify_cell(login_raw)
login_from_email_col = classify_cell(email_raw)[1]
```

**教训**: 元组解包这种错不会报错, 只会让数据静默走错分支。

### 3.2 `classify_cell` 丢弃备注, 提醒永远不出现

原来写 `email_from_email_col, email_note = classify_cell(email_raw)`,
但 `classify_cell` 第二个位置是**用户名**, 不是备注, 所以 `email_note` 恒为空,
「一格里有 2 个邮箱, 只取了第一个」这个提醒从来没打印过。
新增 `email_note_of()` 单独取备注。

### 3.3 `--cols "-,email,username"` 用不了(argparse 坑)

argparse 看到以 `-` 开头的值会以为那是另一个选项, 直接报 `expected one argument`。
但「跳过第一列」天生就长这样。加 `normalize_argv()`: 解析前把 `--cols 值` 合并成 `--cols=值`。

### 3.4 `--limit` 语义是错的(静默跳过更多人)

原来实现成「取前 N 个**还没处理的**人」, 于是续跑已经跳过的人被排除在 N 之外 ——
`--limit 2` 实际处理了表里第 4、5 行, 而用户以为在看前 2 行。
改为按**表里原始行号**(`Record.row`)判断, 并把同一段行里的重复行/空行一起算进 N;
没轮到的行标记 `skipped_unprocessed`(「--limit 截断」), 明确说明不是失败。

### 3.5 `github.com/dave` 被误判成打错的文件路径

「长得像路径就报找不到文件」的检查把 `https://github.com/dave`、`github.com/dave`
这类输入也拦了。加 `_declared_as_identity()`: 已经能解析成邮箱/用户名/个人主页的, 就别当文件。

### 3.6 「空行」被算成「排除」

完全空白的行(含末尾空行)原来会占一行并显示「排除了 N 行」, 让人以为数据有问题。
改成在读表阶段就丢掉。另外 `#` 注释行原来被当成用户名, 加进跳过逻辑
(示例名单文件 `users.example.txt` 里就有注释)。

## 4. 落盘测试抓到的一个隐蔽 bug: 状态值撞车

`S_FAILED` 和 `T_FAILED` 都写成了字符串 `"failed"`, 于是它们在
`ORG_LABEL` / `TEAM_LABEL` / `REMEDY` 里**是同一个字典键** ——
`REMEDY` 里 team 那条把组织那条**静默覆盖**了。表现:

> 组织邀请失败(404)的行, 拿到的处理措施是
> 「照上面的原因查: 对方是不是组织成员、用户名拼写对不对…token 有没有该 team 的写权限」

建议和失败原因完全对不上。修法: team 档的值一律带前缀
(`team_added` / `team_failed` / `not_requested`), 并新增一项测试**断言所有状态值两两不同**,
防止这类静默覆盖复发。

## 5. 真实数据实跑发现的: 用户名和邮箱对不上

用户给的收集表 `uu们的GitHub用户名和邮箱开盒.xlsx` 共 6 行。实跑过程与结果:

| 轮次 | 命令 | 结果 |
|---|---|---|
| 1 | `--team "NEUP 2026" --execute --limit 2` | 前 2 人**已是组织成员** → 一封邀请邮件都没发, 只走了 team 路径(2 人已在 team, 跳过) |
| 2 | 同一命令重跑 | 同上, 证明续跑/已在 team 判定幂等 |
| 3 | `--limit 4 --execute` | 第 3、4 人预检说「不在组织里」, 发邀请却回 **422** `A user with this email address is already a part of this organization` |

第 3 轮这两个人的数据是这样的: **用户名在 GitHub 上根本不存在**(`GET /users/{login}` → 404),
但**邮箱属于某个已经在组织里的账号**。也就是这行的用户名和邮箱**不是同一个人**(或用户名拼错了)。

**结论(已写进 ARCHITECTURE)**: 「预检说不在组织里」≠「真的不在」。
只有邮箱时预检认不出成员关系(成员接口不返回邮箱), 靠发邀请时的 422 兜住;
422 判定为 `already_member`, **不会给对方发邮件**。

顺带确认了 `parse_conflict_message` 只认 GitHub 的明确措辞, 不用宽松的「含 already 就算已存在」——
否则 `Name already exists` 这类无关 422 会被误判成「已加入」, 把真失败吞掉。已补测试用例覆盖。

**副作用: 这一次实跑没能验证「邀请真的发出去(201)」那条主路径** ——
前 4 行里没有一个是「不在组织里且用户名/邮箱能邀请成功」的人。这条路径补在下一节。

## 5.1 用假客户端把 201 路径补上

既然真实样本拿不到, 就写 `_test/run_path_tests.py`(17 项): 用一个只实现
`user_id()` 和 `request()` 的 `FakeGitHub`, **驱动真实的 `process_org_invites` /
`process_team`**, 检查脚本真实发出的请求体和各响应码的落点:

- 201 -> `invited` / `committed`; 有用户名时请求体必须是 `invitee_id` 且**不带** `email`;
  只有邮箱时才是 `email`, 并附上「未验证点不动」的提醒
- 用户名解析不到: 有邮箱就**退回邮箱邀请**, 没邮箱才判失败且**不发请求**
- 422 `already a part of this organization` -> `already_member`;
  无关的 422(`Name already exists`)-> **必须判失败**(这是防误判的负向对照)
- 403 / 404 -> `failed` 并带对应处理提示
- dry-run -> **零请求**, 状态为 `planned`
- 已在 team -> **一次 PUT 都不发**(发了就会把 maintainer 降级)
- 201 之后落盘正确, 且**续跑能索引到这个人**

写这套时又暴露一个「测试自己的坑」: 403/404 那两条一开始给的行只有用户名没有邮箱,
于是脚本在「用户名解析不到且没邮箱」那道保护上提前返回, **根本没发出 POST**,
测试看起来在测 403 其实什么都没测。补上邮箱后才真正走到响应分支。

## 8. 后续: 两位「待重跑」的人其实是用户名拼错了

用户反馈: 姜同学明明已经进组织了, 但重跑还是显示「待对方接受组织邀请」。查下来有两层原因。

### 8.1 我一度加过一次「活查成员关系」——后来砍掉了

**先按错误的方向改了一版**: 我猜「GitHub 成员列表有延迟, 所以对方成了成员但快照里没有他」,
于是让 `process_team` 在拿不准时额外调一次 `GET /orgs/{org}/members/{username}` 单查。

**用户质疑「是不是根本不用改代码, 这就是用户输入错误」——他是对的。** 复盘:

- 那个「列表延迟」的假设**从头到尾没有任何实测证据**。反证是: 我 13:53 和 13:55 连着跑两遍,
  同一个人的「已是成员」判定两次都稳定, 没出现延迟。
- 这个活查**在本次问题里一次都没被用到** —— 两个人都在它之前就因「用户名不存在」`continue` 了。
- 它的代价是每个「有历史但不在快照里」的人身上多一次 API 调用(失败路径)。

所以已**整块还原**: 删掉 `is_org_member()`、`membership_cache` 参数、以及围绕它的
「本次是否刚发邀请」分支(`invited_now`)。现在 `process_team` 只信预检那一份成员快照,
代码回到最小改动。

**留下的教训**: 不要为了一个自己没验证过的假设去加防御性复杂度; 先把真正的因果查清
(这里是数据拼写错误), 再决定代码要不要动。

### 8.2 真正的原因: 用户名拼错了 (相邻字符打反)

单查之后仍然不是成员, 说明这人确实不在组织里。再往下查发现:

| 表里填的(占位) | `/users/{login}` | 实际正确的用户名(占位) | 正确的那位在组织里? |
|---|---|---|---|
| `u5er_na3e` | 404 | **`user_name`** | 是 |
| `usr_naem` | 404 | **`usr_name`** | 是 |

两个人的用户名都是**相邻字符打反**。表里那个名字在 GitHub 上压根不存在, 所以
「等待对方接受」这句话**永远等不到**。真正的账号早就是组织成员了, 只是没进 team。

改成正确拼写后重跑: **6 人全部已是组织成员 + 全部进入 NEUP 2026, 退出码 0**。

### 8.3 认知纠正: 「网页搜得到」不等于「这个用户名存在」

用户拿 GitHub 网页搜索结果质疑「那个打错的名字不就是用户名吗」。实测把字段摊开:

```
搜索 u5er_na3e  -> total_count=1, 但 login='user_name'   (精确搜 in:login 是 0 结果)
搜索 usr_naem   -> total_count=0
GET /users/u5er_na3e -> 404     GET /users/user_name -> 200
```

GitHub 网页搜索是**模糊/全文**匹配, 而且会把**用户输入的那个词加粗高亮** ——
看起来就像账号名, 实际是「你搜的词」。那 1 条结果是它把相近的账号推给你。

**判断用户名是否存在, 只认 `GET /users/{login}` 的 200/404**, 不要用网页搜索的条数。

### 8.4 顺手加的保护

- 新增状态 `用户名不存在`: 当某人不是组织成员、且 `GET /users/{login}` 返回 404 时,
  不再给「等对方接受」这种没用的话, 而是直说查不到这个用户名、去核对拼写。
  这个状态**计入失败**(退出码 1), 不会被悄悄咽掉。
- 控制台把 team 那一步分成三种说人话的情况:
  「邀请刚发出, 等对方接受后重跑」/「上次发过至今不是成员, 请他确认用户名」/
  「用户名不存在, 什么也做不了」。
- 措辞上加了「也可能是对方把资料设为私密」, 因为 404 不排除这种可能。
- 新增 5 项回归测试(路径测试 17→22 项), 覆盖: 用户名存在但还不是成员→待重跑零 PUT、
  本次刚发邀请→直接待重跑、同一人只查一次存在性、用户名不存在→明确报错且计入失败、
  该状态的 CSV 落盘。
